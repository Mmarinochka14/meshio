# Meshio Project Style Guide

Эта инструкция обязательна для любых изменений в проекте Meshio.

## Главный принцип

Проект уже имеет собственную визуальную систему. Новые изменения должны
продолжать существующий стиль, а не заменять его. Нельзя ломать уже настроенные
размеры, сетки, цвета, анимации и привычные сценарии без явного решения.

## Цвета

- Использовать CSS-переменные из `frontend/src/styles/global.css`.
- Основной акцент проекта: фиолетовая система `--color-purple-dark`,
  `--color-purple`, `--color-purple-light`, `--color-purple-hover`.
- Новые акцентные цвета допустимы только для смысловых состояний:
  зелёный для успеха, подтверждения, добавления;
  красный для ошибки, удаления, отмены или опасного действия.
- Не добавлять новые синие, оранжевые, жёлтые или другие акцентные палитры без
  явного запроса.
- Если нужен выразительный CTA, использовать фиолетовый градиент из уже
  существующих purple-переменных.

## Размеры и сетка

- Сохранять текущий принцип размеров: элементы, отступы, радиусы, иконки,
  высоты и типографика в основном задаются через `vw`, как в существующих CSS.
- Не переводить глобальные размеры на `px`, `rem`, `clamp()` или новую систему
  без отдельного согласования.
- Перед изменением адаптива смотреть существующие media-блоки в этом же файле и
  продолжать их логику.
- Не менять глобальные font tokens, контейнеры и header/body offsets, если
  задача не про это напрямую.

## Компоненты и поведение

- Использовать уже существующие компоненты, классы, icons и API helpers.
- Новые элементы должны повторять уже существующие принципы:
  одинаковые hover-анимации, одинаковые border-radius, одинаковые состояния
  загрузки/ошибки/пустого списка.
- Не использовать `alert()` для штатных ошибок интерфейса. Показывать inline
  сообщение в стиле страницы.
- Не дублировать бизнес-логику, если уже есть helper, store или API-функция.
- Не делать заглушки, которые выглядят как финальный функционал. Если сценарий
  пока локальный, это должно быть понятно из кода и не ломать UX.

## UI/UX

- Пользователь должен интуитивно понимать, что делать: одинаковые действия
  выглядят одинаково на всех страницах.
- Внутри одной системы (личный кабинет, каталог, карточки списков, формы)
  одинаковые сущности обязаны иметь одинаковую ширину, отступы, радиусы,
  фон, borders, hover и active-состояния. Нельзя делать вкладки личного
  кабинета разной ширины или разного визуального языка без явной причины.
- Перед правкой одной вкладки личного кабинета сравнивать соседние вкладки той
  же роли: история покупок, поддержка, уведомления, способы оплаты и настройки
  должны выглядеть как части одной системы.
- Для подтверждения/опасных действий использовать модалки или уже существующий
  паттерн подтверждения.
- Для фильтров, сортировки, вкладок и карточек использовать единые стили и
  терминологию.
- Не перегружать страницы новыми блоками, если они не помогают основному
  сценарию.

## Работа с существующим кодом

- Не удалять и не переписывать существующий функционал без необходимости.
- Перед правкой смотреть соседние файлы и копировать локальные паттерны.
- Если файл уже имеет user changes, работать поверх них аккуратно.
- Любая новая страница личного кабинета должна поддерживать роли:
  buyer, seller, admin, и не смешивать их сценарии.

## Проверка

- Backend проверять командой:
  `backend/.venv/Scripts/python.exe manage.py check`
- Frontend проверять через `npm run lint` и `npm run build`, если `node/npm`
  доступны в окружении.
